## 项目背景与解决痛点

我开发这个工具的初衷，源自自己在整理和交付数字媒体素材时的切身体会。在课程作业提交、海报设计和小型内容团队协作中，经常需要交付大批海报、封面图、社交媒体卡片和切图。光看文件名是否整齐根本不够：
1. **肉眼核对极易遗漏**：尺寸稍有偏差、导出比例被拉伸变形、或者单张图片体积超出了发布平台的限制，一张张用看图软件查极为耗时且容易眼花看漏；
2. **多交或漏交难以拦截**：交付目录里常常会不小心混入未登记的导出草稿，或者漏掉某张关键配图；
3. **验收缺少留档与复核凭据**：每次靠人工肉眼盯，不仅不能自动化重跑，出了问题也无法追溯。

与其每次靠人工提心吊胆地核对，不如把验收标准直接写成结构化的 JSON 规格清单。片盒点检正是我为此打造的命令行工具：它纯只读地扫描交付目录，一键核对所有素材是否符合清单要求，并生成直观的中文 HTML 报告与机器可读的 JSON 报告，让验收可重复、有留档、便于协作复核。

需要特别说明的是，**我将这个工具定位为严格的“检查工具”，不做任何“图像生成”**。它不解码像素、不改动输入文件、不评判画面审美，也不产出图片，专门解答“交付的这批素材与清单规格是否完全一致”。

## 本次提交功能范围（已全部实现）

我**明确将 BMP、TIFF 与 aspect 宽高比校验纳入本次提交范围**。目前仓库主分支已经全部实现并交付了以下核心功能：

1. **六大主流光栅格式的尺寸解析**：
   - **PNG**：校验数据块边界、CRC32 校验码与 IHDR/IDAT/IEND 基础容器结构，解析画布宽高；
   - **JPEG**：扫描 SOF 标记，解析 APP1 中的 EXIF Orientation（兼容大端 MM 与小端 II 字节序，方向 5–8 自动换算为正确显示方向的宽高），设置 4 MiB 元数据安全扫描上限；
   - **WebP**：解析 RIFF 容器边界与填充，支持 VP8（有损）、VP8L（无损）、VP8X（扩展画布）尺寸头；
   - **GIF**：解析 GIF87a/89a 逻辑屏幕描述块（LSD）获取画布尺寸；
   - **BMP**：支持标准 BITMAPINFOHEADER 及 OS/2 BITMAPCOREHEADER，妥善处理正负高度；
   - **TIFF**：解析 TIFF 文件头与 IFD，读取 ImageWidth 与 ImageLength 标签，兼容 II/MM 字节序及 SHORT/LONG 类型。
2. **精确宽高比校验（aspect）**：
   - 清单素材项支持可选 `aspect` 字段（如 `"16:9"`、`"1:1"`、`"4:3"`）；
   - 我在底层采用整数交叉相乘（$W \times H_{req} == H \times W_{req}$）精确核对，彻底避免浮点数精度截断误差。
3. **严格的清单防呆校验**：
   - 拒绝未知字段、拒绝同一对象中的重复键名（如重复声明 `width`）、拒绝浮点小数规格（必须显式为整数），在扫描文件前直接报错中断并指示位置，杜绝规格被静默改写或忽略。
4. **容量预算与内容指纹**：
   - 支持单素材 `max_bytes` 上限及整包目录 `max_total_bytes` 总容量预算；
   - 记录清单文件本身的原始 SHA-256 摘要（固定验收审计基准）；
   - 支持单素材 `expected_sha256` 强一致比对，并智能提示相同指纹的潜在重复图片。
5. **绝对的安全与只读保证**：
   - 纯只读模式：对输入素材只进行流式只读访问，绝不修改、不重命名、不删除任何文件；
   - 路径安全过滤：素材路径仅允许合法相对路径，强制拒绝 `..` 越界、反斜线 `\` 与绝对路径，扫描不跟随符号链接。
6. **双模报告生成**：
   - 自动输出中文 HTML 报告（所有文本及文件名均做防 XSS 转义，直观高亮展示要求值、实际值、差异项与通过率统计）；
   - 同步输出机器可读的 JSON 报告，便于流水线无缝集成。

## 当前技术限制与使用边界

为了保证评估客观真实，我主动声明以下技术边界：

1. **不解码像素数据**：我将本工具定位为交付前的“规格预检器”，不解压缩图像数据流（如不解码 PNG IDAT、WebP VP8 像素），不渲染画面；
2. **不判断色彩空间与视觉质量**：不解析 ICC 配置文件，不评估图像是 sRGB 还是 Display P3/CMYK，不进行美学或画质打分；
3. **不保证全部图像格式规范的完备合规**：工具只校验尺寸头、容器基础结构及关键块 CRC，不作为标准图像格式规范的严格合规性判定工具；
4. **真实试用的边界说明**：当前的真实试用验证了工具对真实文件的解析可靠性，但由于测试样本量较小且规格来自真实文件提取，尚未大规模进入商业交付流水线收集外部用户反馈。

## 选题区分与生态定位

片盒点检专注在**“素材交付验收”**，不做**“图像生成或格式转换”**。

在选题调研时，我注意到 MoonBit 生态里有两个相邻但定位不同的项目：
- `moonbit-posterkit`：是数据驱动的海报与封面生成 DSL，负责**生成**图片；
- `MoonBitMark`：负责文档与图片的格式转换，属于**转换**工具；
- **片盒点检（MediaPack Audit）**：负责**验收**交付成果。

三者在实际工作流中完全互补：可以用 posterkit 生成海报，用 MoonBitMark 转换配图，最终在交付前使用片盒点检对整包素材做一次快速、严格、可留档的合规性核验。
